# xlengine — 自研电子表格引擎

从底层自写的 Excel 语义表格引擎，C++17，**零第三方依赖**（只用标准库 + zlib）。

包含：495 个函数、xlsx 读写、图表（含落盘到 xlsx）、PDF 矢量导出、终端网格界面。

## 已复刻的 Excel 语义暗坑

这些是自研最容易翻车、也最决定"像不像 Excel"的地方，全部有测试守着：

- **1900 假闰日**：序列号 60 对应不存在的 1900-02-29，`DATE(1900,2,28)=59` 而 `DATE(1900,3,1)=61`
- **`-2^2 = 4`**：一元负号优先级高于幂运算（按 C 系语言习惯会算成 -4）
- **`MOD(-3,2) = 1`**：余数与除数同号，`fmod` 会给出错误符号
- **`INT(-2.5) = -3`**：向下取整，不是向零截断
- **排序序**：数字 < 文本 < 逻辑值，故 `"a">1`、`TRUE>1` 均为 TRUE
- **惰性求值**：`IF(TRUE,1,1/0)=1`，未选中分支不求值
- **顶层标量 vs 区域元素**：`SUM("abc")` 报 `#VALUE!`，而区域内的文本静默忽略
- **NPV 与 IRR 的折现约定不同**：NPV 的 values[0] 在第 1 期，IRR 的在第 0 期不折现
- **BIN2DEC 的补码判定**：只有达到 10 位宽且首位是高位数字才按负数，`"1010"=10` 而 `"1111111111"=-1`
- **循环引用** → `#CALC!`，不死循环

## xlsx 读写

纯 C++ 自实现，不依赖 libzip / minizip / expat。

**已通过 openpyxl 双向交叉验证**（含图表、多表、中文表名）：
- 写出 → openpyxl 读：中文表名、中文文本、数字、布尔、错误值、公式（含 `参数!B1` 跨表）全部正确
- openpyxl 写 → 我读：公式重算结果一致、跳空列定位正确

### 一个必须记下的教训：zlib 格式 ≠ raw deflate

第一版 ZIP 用 `compress2` 写、自己的 reader 用 `uncompress` 读——**自洽但不符合规范**：
`compress2` 产出的是带 2 字节头和 Adler-32 尾的 zlib 流，而 ZIP 的 method 8 要求裸 deflate。
Python `zipfile` 报 `invalid stored block lengths`，Excel 也会拒绝。

**结论：自写格式时，自测只能证明自洽，必须引入第三方实现交叉验证。**
`make verify` 就是干这个的。

### 图表落盘

图表不只是画出来，还能存进文件让 Excel 继续编辑。

**OOXML 的类型映射与直观分类不同**，这是最容易写错的地方：

| 直观类型 | OOXML 图族 | 区分参数 |
|---|---|---|
| 柱形 / 堆积柱 | `c:barChart` | `barDir=col` + `grouping` |
| 条形 | `c:barChart` | `barDir=bar` |
| 折线 | `c:lineChart` | `grouping=standard` |
| 面积 / 堆积面积 | `c:areaChart` | `grouping` |
| 饼图 | `c:pieChart` | — |
| 散点 | `c:scatterChart` | X/Y 都走数值轴，用 `xVal`/`yVal` |

数据两种写法，**语义差别很大**：`numRef` 引用区域→图表与单元格联动；`numLit` 内联值→脱钩。

部件清单（缺任何一个 Excel 都会报文件损坏）：

```

xl/drawings/drawingN.xml                锚定位置
xl/drawings/_rels/drawingN.xml.rels     drawing -> chart
xl/worksheets/_rels/sheetN.xml.rels     sheet  -> drawing
[Content_Types].xml                     chart / drawing 两个 Override
```

## 引用重写与填充

`src/refshift.cpp`。选中区域按 `Ctrl+D` 向下、`Ctrl+R` 向右填充，公式里的相对引用自动跟着走。
把 A1 的 `=B1*2` 拉到 A3，必须变成 `=B3*2`。

**不能靠正则改公式。** 字符串字面量里的 `"A1"` 不是引用，正则替换一定会误伤。
必须走词法器的 token 流：只有 `Ref` 平移，`Str` 原样保留。

**整列/整行引用在词法器里根本不是引用。** `B:B` 里的 `B` 没有行号，`parseCellRef` 会拒绝它，
出的是 `Ident`；`1:1` 里的 `1` 出的是 `Num`。只有看到"标识符 冒号 标识符"这种 token 组合才能断定。
少这一步，填充 `=SUM(B:B)` 时列号就不会跟着走。

**越界必须变成 `#REF!`，不能夹取到边界。** 夹取会静默指向一个错误的单元格，用户根本发现不了。

## 数字格式（number format）

`src/numfmt.cpp`。这是"像不像 Excel"最关键的一块：单元格里存的是 `DATE(2026,9,27) = 46262`，
用户看到 46262 是没法用的，必须靠格式码显示成 `2026-09-27`。

格式码最多 4 段（分号分隔）：**正数 ; 负数 ; 零 ; 文本**。只有 1 段时它适用于所有数。

```
0 # ?      数位占位（0 强制、# 可选、? 补空格对齐）
. ,        小数点 / 千分位；末尾逗号表示除以 1000
%          乘 100
E+ e+      科学计数
yyyy mm dd 日期（mmm 缩写、dddd 星期）
h mm ss    时间；AM/PM
[h] [m]    累计时长（不取模）
@          文本占位
\x "..."   字面量
[Red]      颜色
[>0]       条件段
```

**能存进文件**：xlsx 读写打通了 `s`(xf) → `numFmtId` → `formatCode` 这条链，
openpyxl 读回来说 `#,##0.00`、`0.00%`、`yyyy-mm-dd` 全都对得上。内建 ID 0..49
直接引用，其余从 164 起分配自定义 ID。

### 实现里三个不能靠直觉写的地方

- **`m` 是歧义的**：`h:mm` 里是分钟，`yyyy-mm` 里是月。只判断"前面有没有 h"不够 ——
  `mm:ss` 没有 h 但 mm 仍是分钟，所以要在解析前先扫一遍整段定上下文。
- **整数部分必须从右往左分配数字**。`#` 是可选位，从左往右写会把 `#,##0` 显示 5 变成 `005`；
  而模板放不下的高位数字要插在**第一个数字占位符**处，不能一律放最前 ——
  否则 `"合计:"0` 显示 42 会变成 `4合计:2`。
- **负号不能重复加**。段里若已写了 `-` 或用括号包住，就由段负责符号，
  否则会出现 `--5.50` 或 `-(1,234)`。

另外：分号在引号内和方括号内不是分隔符；日期格式里的逗号是标点不是千分位
（`mmmm d, yyyy` 少了这条会变成 `September 27 2026`）。

## 条件格式

`src/cf.cpp`。支持 6 类规则：

| 类型 | 含义 | 命令示例 |
|---|---|---|
| CellIs | 与数值比较（8 种运算符） | `:cf >3 fill=FF0000` |
| Expression | 自定义公式 | `:cf expr A1>2` |
| Top10 | 前/后 N 项（可百分比） | `:cf top 3 bold` |
| AboveAverage | 高于/低于区域均值 | `:cf above fill=FFFF00` |
| Duplicate | 重复值 | `:cf dup` |
| Unique | 唯一值 | `:cf uniq` |

`:cf` 无参列出，`:cf clear` 清空。不给样式时默认红色填充——否则规则生效了也看不出来。

### 三个 OOXML 层面的坑

- **条件格式样式走 `dxfs`，不是 `cellXfs`**。普通单元格用 `xf`（存 `numFmtId/fontId/fillId/borderId`），
  条件格式用 `dxf`，而 `cfRule` 里只有一个 `dxfId`。
- **`conditionalFormatting` 在 `sheetN.xml` 里有位置约束**：必须在 `mergeCells` 之后、
  `drawing` 之前；`dxfs` 在 `styles.xml` 里必须在 `cellStyles` 之后。顺序错了 Excel 报文件损坏。
- **`dxfId` 要二次回填**。读文件时 `cfRule` 先于 `styles.xml` 被解析到手，
  此时 `dxfs` 还没读出来，只能先记下 `dxfId`，等 `styles.xml` 解析完再回填样式。
  少了这一步就是"规则在、样式没了"。

### 判定语义

**公式是相对区域左上角书写的**。sqref 为 `B1:B5`、公式写 `A1>25` 时，
对 B4 求值的语义等价于 `A4>25` —— 要按与左上角的偏移量平移相对引用，
复用 `refshift` 的同一套规则，与"填充"行为一致。

Top10 / AboveAverage / Duplicate 这三类要先看整个区域才能判定（阈值、均值、出现次数），
所以对外提供的是**批量**接口 `resolveCfStyles()` 而不是"查单格"。
逐格调用会把同一区域重复统计 O(n) 次，大表上退化成 O(n²)。

**已通过 openpyxl 交叉验证**：3 条规则的 type / operator / dxfId 全部正确读回，
且 dxf 上的红色填充与粗体确实挂着。

## 数据验证

`src/dv.cpp`。与条件格式结构相似（规则挂在区域上），但语义相反：
**条件格式只影响显示，数据验证要拦住写入**。

| 类型 | 命令示例 |
|---|---|
| 整数 | `:dv whole 1 100` / `:dv whole >=0` |
| 小数 | `:dv decimal 0 100` / `:dv decimal >=0` |
| 序列 | `:dv list 是,否,待定` |
| 文本长度 | `:dv len <=5` |
| 自定义公式 | `:dv custom A1>0` |

`:dv show` 列出，`:dv clear` 清空，可加 `err="提示"`、`warn`、`info`。

### 三个实现上的要点

- **必须在写入前判定**。写进去再判就晚了 —— 非法值已经在表里了。
  判定对象是用户键入的字面值，不是公式结果（公式要等重算才知道）。
- **拒绝后必须提前返回**。否则状态栏会被后面的"已写入 A2"覆盖，
  用户看到写入成功而实际上什么都没写 —— 这比直接崩溃更难发现。
- **`list` 与"列出规则"命令撞名**。`:dv list` 优先当类型处理（不带参数会报
  "list 需要候选项"）；列出规则改用 `:dv` 或 `:dv show`。

### 判定细节

- **整数判定用 `trunc` 比较**，不能用 `fmod(d,1)==0` —— 对很大的数后者精度不够。
- **文本长度按码点数算**。中文按字节算会变成 3 倍，规则形同虚设。
- **date / time 退化为序列号比较**，界面层不做日期解析，所以"日期区间"这类规则体验受限（已诚实标注）。

**已通过 openpyxl 交叉验证**：3 条规则的 type / operator / formula 全部正确读回，
且 `list` 确实没有写 `operator` 属性（Excel 不接受）。

## 性能：增量重算

`src/depgraph.cpp` + `src/precedent.cpp`。先量后改，工具是 `tools/prof`（`make demo` 会跑）。

### 改之前的热点

```
改 1 格 + 全量重算 × 20    406 ms   （单次 20.3 ms）   ← 2 万条公式
```

`recalc()` 把**全部**公式标脏重算，改一格也是 O(全部公式)。表一大，每敲一个键都要等。

### 改之后

| 依赖形态 | recalc（全量） | recalcDirty（增量） | 提速 |
|---|---|---|---|
| 局部依赖（每条只依赖本行） | 4.75 ms | **0.166 ms** | **29×** |
| 窗口依赖（SUM 5 格滑窗） | 15.7 ms | **0.245 ms** | **64×** |

### 三个关键点

**1. 依赖图 + 脏标记传播。** 每条公式记前驱（读了哪些格子），反向建后继表，
改动时只把受影响的格子标脏。**求值顺序不重要** —— 脏格子的 `evaluated` 都是 false，
求值 A 时会递归触发 B。所以不需要拓扑排序。循环引用也不破坏这个性质。

**2. 标脏必须同时清缓存。** 依赖图只是"谁该重算"的索引，真正决定是否重算的是
`CellRec::evaluated`。只标脏不清缓存的话，recalcDirty 看到 `evaluated=true` 直接跳过，
**结果是"跑得飞快但数是旧的"** —— 这个 bug 不报错，比慢危险得多。第一版就踩了。

**3. `usedRange()` 原来是全表扫描。** O(n)，却被调用在 `setValue`（每次编辑）和
整列引用求值裁剪里。改一格变成 O(全部格子)，**把增量优化的收益全吃掉了**。
现在是写入时增量扩张、删除时才失效重算。

### 保守策略

超大区域（>65536 格）、整列引用的边界未知、lambda 体内的引用 —— 这些不建边，
标记为"保守型"每次都重算。宁可重算一条，也不为它建百万条边拖垮整张表。
保守格子单独维护一份列表，`markAllConservative()` 不再每轮扫全表。

### 内存：每格从 384 降到 192 字节

`CellRec` 原本内联了数字格式码（`std::string`，32 字节）和视觉样式
（`CellStyle`，152 字节）—— 合计 184 字节，**而绝大多数格子两个都没有**。

改成存在 Sheet 的两个稀疏 map 里，只有真正设过的格子才占空间。

同口径 A/B（等价结构体，20 万格，只改布局）：

```
旧布局（numFmt+style 内联）: 384.0 字节/格
新布局（稀疏外置）        : 192.0 字节/格     ← 减半
```

项目内实测（20 万格纯常量）：254.1 字节/格。

**保留了一个刻意的行为**：`setNumFmt` / `setStyle` 仍然确保 `cells_` 里有记录。
只设格式、没设值的格子也必须能被导出，否则存盘后格式会静默丢失 ——
省下来的是 CellRec 里那 184 字节，不是这条记录本身。

代价：每格都带格式时反而多占（335.9 vs 254.6 字节/格），因为多了一次
map 查找。真实工作簿里只有表头与汇总列有格式，这个代价可以忽略。

### 惰性区域：不再为每个 SUM 分配一次数组

`SUM(A1:A100)` 原本要先把区域 materialize 成 `Array2D`（一次 `make_shared`
\+ 每行一个 `vector` + 逐元素拷贝），再由 `flattenArgs` 摊进一个
`vector<Value>` 才算 —— 两处中间容器都是为了"先攒起来再算"，
而聚合函数根本不需要攒。

改成：区域求值只记坐标（`Value::rangeRef`），由支持惰性的函数按坐标直接遍历。

同一台机器上的 A/B（`-DXLE_NO_LAZY_RANGE` 编译出基线，同环境对比，
每档 7 轮取最佳 —— 单次计时在这个环境噪声极大，不同时段没有可比性）：

| 公式 | 基线（展开后遍历） | 惰性 | 提速 |
|---|---|---|---|
| `SUM(A1:A5)` | 0.455 us | **0.343 us** | 1.33× |
| `SUM(A1:A100)` | 5.852 us | **2.182 us** | **2.68×** |
| `AVERAGE(A1:A100)` | 5.738 us | **2.268 us** | 2.53× |
| `COUNT(A1:A100)` | 5.980 us | **2.180 us** | **2.74×** |
| `MAX(A1:A100)` | 5.717 us | **2.328 us** | 2.46× |
| `STDEV.S(A1:A100)` | 7.605 us | **2.555 us** | **2.98×** |
| `VAR.S(A1:A100)` | 7.723 us | **2.878 us** | 2.68× |
| `DEVSQ(A1:A100)` | 7.801 us | **2.715 us** | 2.87× |
| `A1*2`（无区域） | 0.142 us | 0.139 us | 无退化 |
| `LEN("abc")` | 0.202 us | 0.201 us | 无退化 |

统计类（`STDEV`/`VAR`/`DEVSQ`/`GEOMEAN`/`SKEW`/`KURT` 等）也走同一条路径。
它们原本用 `col2` 先把区域摊成 `vector<Value>`（每元素 104 字节）再转 `double`
—— 中间那层纯属浪费，现在直接按坐标收集 `double`。

**白名单机制**：只有明确改造成惰性遍历的函数拿得到未展开的区域，其余
在进函数前就被展开 —— 正确性由"默认展开"兜底，不用逐个改。
**白名单必须与实际改造严格一致**，多列一个就会让它收到不认识的类型而静默算错。

**一个反直觉的性能坑**：白名单不能无条件查。第一版写成
`if (!supportsLazyRange(u)) { ... }`，于是**每条不涉及区域的公式也要白跑
二十次字符串比较** —— 实测 `LEN("abc")` 慢了 55%（0.195 → 0.305 us）。
改成先扫参数（只做类型检查，很便宜）、确认有区域才查白名单后，
`LEN("abc")` 回到 0.201 us，与基线一致。

### 求值深度上限（顺带修掉一个段错误）

改这块时压力测试崩了：`1+1+...（一万项）` 在求值阶段递归一万层把栈打爆。
解析器有 4000 层上限，**求值没有** —— 用户只是写了个长公式，进程就没了。

加了 `kMaxEvalDepth`。这个值是**实测**出来的，不是随手定的：

```
9000 层：安全（返回 #NUM!）
10000 层：段错误
```

取 8000。够用的理由：Excel 公式长度上限 8192 字符，`1+1+...` 每 2 字符一项，
最坏约 4096 项 —— 8000 有近 2 倍余量。**超出 Excel 长度的公式返回 `#NUM!`
是安全拒绝，不是功能缺陷**：它本来就不是合法输入。

压力测试相应拆成两档：4000 项（Excel 合法范围内）必须算对得 4001；
20000 项只要求**不崩溃**且返回错误值。

**一个值得记住的坑**：栈帧。我最初把深度守卫写成 `eval()` 包一层
`evalUnchecked()`、把展开包一层 `evalBinaryEx()` —— 每层递归多一次函数调用
就让万项连加从"能算"变成段错误。最终把展开内联进 `evalBinary`（加 `ctx` 参数），
守卫只留一个 RAII `bool`，才把栈帧压回去。

### 跨表传播要收敛，不能固定趟数

跨表依赖可能成链（A 引用 B，B 引用 C），固定两趟会在链更长时留下脏格子，
表现为"跨表的数偶尔不更新"——间歇性失败，极难复现。改成收敛循环（上限 8 趟）。

### 顺带修掉的一个既有 bug

写跨表测试时发现：`Workbook::sheetByName` 读的是 `SheetRec::name`，
而 `Sheet::setName()` 只改 Sheet 自己那一份。于是**"建表后改名"的表在查找里永远查不到**，
跨表引用一律 `#REF!` 且不报错。现在统一以 Sheet 自身的名字为准。

## 定义名称（命名区域）

`=SUM(销售额)` 而不是 `=SUM(B2:B5)`。终端：`:name 销售额 B2:B5` 定义，
`:name` 列出，`:name del 销售额` 删除。

存在 `workbook.xml` 的 `<definedNames>`，求值时由 `eval.cpp` 的
`NodeKind::Name` 分支处理。

### 查找顺序不能反

```
LET(x, 99, x)  ->  99       LET 作用域是公式内部的局部绑定，优先级更高
x              ->  定义名称的值
```

先查 LET、再查定义名称。反了的话，公式里的 `LET(x,...)` 会被外部的持久名称遮蔽。

### 名字必须在写入时就拒绝，不能等到求值

`A1` 这种名字**永远不会被查到** —— 词法器见到它产出的是 `Ref`，不是 `Ident`。
如果允许定义，用户会得到"看起来成功、实际永远无效"的名称。所以
`addDefinedName` 会拒绝：数字开头、像单元格地址（`A1`/`AB12`）、含空格或运算符、
`TRUE`/`FALSE`、单字母 `R`/`C`。

### 两个实现上的坑

- **定义文本必须带表名 + 绝对引用**（`销售数据!$B$2:$B$5`）。
  不带表名的相对引用在别的表的公式里会被解析到错误位置——**静默算错，比报错更难发现**。
- **重置顺序**：`<definedNames>` 在解析 `<sheets>` 之后就填好了，
  而"逐表加载"那一步还会重置 `images_`/`notes_` 等容器。我第一版把
  `definedNames_.clear()` 也放进了那个重置块，结果**刚解析出来的名称被立刻清掉**，
  表现为"存盘时写了、读回来是空的"，且不报任何错。已改为在 load 开头统一清一次。

### 一个隐蔽的使用风险

命名区域把 `B2:B5` 隐藏成了"销售额"，写公式时看不出边界。
把 `=MAX(销售额)` 写在 **B4** 时，B4 自己就落在 B2:B5 里，会变成自引用 `#CALC!`。
写示例时我确实踩了这个——汇总公式要放在数据区之外。

**已通过 openpyxl 交叉验证**：3 个名称（含中文名与常量型）全部正确读回，
且 `A7` 的 `SUM(销售额)` 公式与 `B7` 的缓存值 165 都对。

## 嵌入图片

`src/image.cpp`。终端：`:img` 把当前表的图表光栅化成 PNG 后嵌入，
`:img list` 列出，`:img clear` 清除。

### 与图表共用 drawing，但 XML 完全不同

| | 图表 | 图片 |
|---|---|---|
| 元素 | `<xdr:graphicFrame>` | `<xdr:pic>` |
| 引用属性 | `r:id="rId1"` | `r:embed="rId1"` |
| 关系类型 | `.../chart` | `.../image` |

这两个属性名**不能互换**。写错了 Excel 会说文件有问题或直接不显示图片。

### 三件套，且 Default 与 Override 机制不同

```
xl/media/imageN.png                         图片本体（二进制）
xl/drawings/_rels/drawingN.xml.rels         image 关系
[Content_Types].xml  <Default Extension="png" .../>
```

注意第三条：部件 Override 是**按路径**登记的（如 `/xl/charts/chart1.xml`），
而图片是**按扩展名**登记 Default。两者机制不同，混用会导致文件打不开。

### 三个实现上的坑

- **Content_Types 在部件写入之前就输出了**，所以用过的扩展名必须在 save 开头
  先扫一遍收集，不能等到写 media 时才记。我第一版就是漏了这步，
  结果 media 与 drawing 都正确、唯独 ContentTypes 缺 Default。
- **ZipReader 没有 `readBytes`**，只有 `readText` 和 `entries()`。
  图片是二进制，必须走 `entries()` 拿原始字节——用 readText 会破坏数据。
- **只有图片、没有图表的表原本不生成 drawing**（与批注那个坑同源）。
  现在改成图表或图片任一存在就生成，rId 按"先图表后图片"顺序分配。

**已通过 openpyxl 交叉验证**：读回 1 张图片、字节数一致、PNG 魔数完整
（`\x89PNG`，证明二进制未被文本化破坏）、锚点 H4 正确、ContentTypes 登记了 png Default。

## 视图属性：列宽、行高、冻结、筛选

`src/view.cpp`。终端命令：`:colw 18`、`:rowh 28`、`:freeze`、`:filter`。

这些属性有个共同特点：**丢了不会报错**。文件照样能打开、自己的 reader 照样能读回来，
只有用户在 Excel 里打开时才会发现表头不再冻结、列宽全没了、筛选箭头消失了。
所以这类功能必须靠 openpyxl 验证真实写进了文件。

### 序列约束与一个隐藏的坑

```
sheetViews → cols → sheetData → autoFilter → mergeCells → conditionalFormatting
→ dataValidations → drawing
```

`cols` 必须在 sheetData **之前**，`autoFilter` 在 sheetData **之后**。

坑在于：`autoFilter` 的输出不能放进 `if (!mergeRects.empty())` 块里——
我第一版就是这么写的，结果**没有合并单元格的表根本不输出 autoFilter**，
表现为"设了筛选但存盘后消失"。测试里往返断言立刻暴露了它。

### 冻结窗格的派生属性

`activePane` 的取值不是随意的：只冻列是 `topRight`、只冻行是 `bottomLeft`、
行列都冻才是 `bottomRight`。写错了 Excel 会选错初始活动窗格，
表现为"打开后光标停在被冻结的区域里"。

`topLeftCell` 是未冻结区的第一个格子，冻结 N 列 M 行时就是 `(N, M)`——
用的是冻结数量本身，不是 +1。

### 列宽合并

相邻且同宽的列合并成一个 `<col min max>`，不合并的话每列一个元素，
文件变大且结构与其他实现不一致。

**已通过 openpyxl 交叉验证**：列宽 16/12、行高 30、冻结在 B2、筛选区域 A1:D5，
全部正确读回。

## 共享公式（`t="shared"`）

xlsx 里一块连续区域的相同公式只写一次文本：

```xml
<!-- 主格 B1：带文本与 ref -->
<f t="shared" ref="B1:B5" si="0">A1*2</f>
<!-- 引用格 B2..B5：只有 si，无文本 -->
<f t="shared" si="0"/>
```

读取时把主格公式按与锚点的偏移量平移后写入每个引用格，
复用 `refshift` 的同一套规则（与"填充"、条件格式判定一致）。

### 为什么要真正展开，而不是保留已算出的值

只保留 `<v>` 里的缓存值**看起来是对的，实际上公式已经死了**——
改了源数据，引用格不会跟着变。所以测试里专门验证了这一点：

```
A1 从 1 改成 100 后，B1 从 2 变成 200     ← 证明公式活着
```

如果只存缓存值，这里会仍然显示 2。

### 两个实现上的坑

- **判别主格靠"有没有 `ref` 属性"，不是靠 `si` 的值**。
  `si="0"` 既可能是主格也可能是引用格，用 `si` 判断会漏掉真正的引用格。
- **外层守卫不能写成 `if (f && !f->text.empty())`**。
  引用格的文本本来就是空的，这样写会把引用格整个跳过、落进常量分支，
  表现为"值对但公式没了"——极难察觉。

找不到主格（文件损坏或 si 不匹配）时降级为已算出的值，并**明确告警**，
不静默丢格子。

## 批注

`src/note.cpp`。与条件格式、数据验证的存储方式不同：批注**不在 sheetN.xml 里**，
而是独立部件 `xl/commentsN.xml`，靠 `sheetN.xml.rels` 的 comments 关系挂上去。

`:note 文本` 添加/修改，`:note` 查看，`:note clear` 删除。有批注的格子在网格里带 ◂ 角标。

### 必须"三件套齐全"

```
xl/commentsN.xml                  批注本体
xl/worksheets/_rels/sheetN.xml.rels   comments 关系
[Content_Types].xml               comments 的 Override
```

少任何一件，Excel 打不开或读不到批注，**而自己的 reader 可能照样报成功**——
因为自写解析器通常不会去校验 rels 与 ContentTypes 的一致性。所以这一项必须靠 openpyxl 验证。

### 两个实现上的坑

- **只有批注、没有图表的表原本不生成 rels**。原代码只在有 drawing 时才写
  `sheetN.xml.rels`，于是这类表的批注会全部静默丢失。现在改成统一生成，
  drawing 占 rId1 时 comments 顺延到 rId2，两者可共存。
- **同名作者要建表去重**。`authors` 表按首次出现编号，comment 用 authorId 引用；
  不建表的话同名作者会重复出现，Excel 里作者列表很难看。

### 与 SciPy 的数值交叉验证

`make xcheck` —— 用 **SciPy / NumPy** 独立计算 687 组结果，与引擎逐项对照。

这是本项目最有力的一类验证：自测只能证明**自洽**，SciPy 是完全独立的实现，
两边对得上才说明**算对了**。覆盖：

| 类别 | 函数 |
|---|---|
| 连续分布 | 正态 / t / 卡方 / F / Gamma / Beta / 对数正态 / 指数 / 威布尔 |
| 离散分布 | 二项 / 泊松 / 负二项 / 超几何 |
| 特殊函数 | erf / erfc / Γ / lnΓ / 四类贝塞尔 |
| 统计量 | 标准差 / 方差 / 偏度 / 峰度 / 分位数 / 相关 / 协方差 / 几何与调和平均 |
| 矩阵 | 行列式 / 求逆 / 转置 |
| 回归 | SLOPE / INTERCEPT / LINEST（多元） |
| 财务 | NPV / IRR（二分求根） |

### 它抓到了一个真 bug

**LINEST 的多元系数顺序反了。** Excel 的系数是**逆序**：最后一个自变量的系数排最前，
截距永远在最后。原实现用正序 —— **单变量时完全看不出差别**（只有一个斜率），
多变量时才前后颠倒：

```
y = 1·x1 + 2·x2 + 3
引擎输出 {1, 2, 3}      ← 正序
Excel 应为 {2, 1, 3}    ← 逆序
```

`LOGEST` 复用同一实现，一并修正。

### 验证本身也要被验证

跑完对照后我做了**变异测试**：故意给 `NORMSDIST` 注入 0.1% 偏差，确认工具能报出
11 项不符。**一个从没失败过的验证等于没有验证** —— 这一步是为了确认它确实在检验，
而不是因为写错了比较逻辑才"全部通过"。确认有效后已还原。

### 参照写错的 5 处（引擎是对的）

| 我写的参照 | 错在哪 |
|---|---|
| `FACTDOUBLE(5)` = 160 | 参照公式写乱了；正确 5!! = 5×3×1 = **15** |
| `BETA(2,3)` | Excel 没有独立的 `BETA()`，只有 `BETA.DIST` —— 引擎报错是对的 |
| `ROUND(2.5)` = 2 | Python `round()` 是 banker's rounding；Excel 是**远离零** → 3 |
| `NPV` 期望值 | Excel 从**第 1 期**折现（values[0] 也折一期），与 IRR 约定不同 |
| `IRR` 期望值 | 用多项式根再变换容易错；改用二分法直接解 NPV=0 |

## 与 LibreOffice 的语义级交叉验证

`make locheck` —— 用 **LibreOffice**（真正的电子表格实现）重算 **150 组公式**并逐项对照。

SciPy 能验证"数值算得对不对"，但验证不了 Excel 的那些**约定**：运算符优先级、
`MOD` 的符号、取整方向、文本与数字的强制转换、错误传播……这些是"像不像 Excel"的
关键，只能拿一个真正的电子表格实现来对照。

做法：公式写进 xlsx → `soffice --headless` 重算并导出 CSV → 与引擎比对。
**必须给单元格设 `number_format`**，否则 LibreOffice 会把 `DATE()` 导出成 `02/29/24`、
`PMT()` 导出成 `-$856.07`，与引擎的裸数值对不上。

### 它抓到了两个真 bug

**1. 中文文本函数按字节截取（严重）**

`LEN` / `LEFT` / `RIGHT` / `MID` / `REPLACE` 原先直接对 `std::string` 按字节操作：

```
LEN("中文abc")             = 9             ← 3+3+3 字节，应为 5
LEFT("中文abc",2)          = "\xe4\xb8"        ← 汉字被切成半个，输出乱码
REPLACE("中文abc",1,2,"X") = "X\xb8文abc"     ← 应为 "Xabc"
```

已抽到 `src/utf8.hpp` 统一按**码点**处理，五个函数共用。

**2. 幂运算符的结合性反了**

Excel 的 `^` 是**左结合**——唯一与常规数学约定相反的结合性。同时**一元负号优先于 `^`**。
两条规则必须同时成立：

| 表达式 | Excel/LO | 引擎（修正前） |
|---|---|---|
| `2^3^2` | 64 | **512** |
| `2^2^3` | 64 | **256** |
| `2^-3^2` | 0.015625 | **512** |
| `-2^3^2` | 64 | **-512** |
| `2^3^-2` | 0.015625 | **1.08** |

修法：`parsePow` 从"递归右边"改成 `while` 循环，且**两侧都用 `parseUnary()`**
——右侧继续调 `parsePow` 就还是右结合，而负号必须先绑到紧邻操作数。

### 已知差异：9 条，如实列出不计失败

| 根因 | 用例 |
|---|---|
| **逻辑值参与比较**（3 条同源） | `TRUE>1`、`1=1=1`、`1<2<3`。Excel 排序序是 数字<文本<逻辑值，逻辑值与数字永不等；LO 把 TRUE 当 1 |
| `SUM("5")` | Excel 把顶层文本型数字转数值得 5；LO 报 `#VALUE!` |
| `SUMIF`/`AVERAGEIF` 内联数组 | LO 不支持把数组字面量当区域（得 0 / `#DIV/0!`） |
| `CELL("row")` | LO 不支持该参数 |
| `TYPE(TRUE)` | Excel 给 4；LO 给 1 |

这些是**判定过的差异**，不是"跳过"。检查器只在真不一致时才记差异——
LO 其实答对的（如 `SUMIF(...,{10,20,30,40})`）不会被差异表掩盖。

### CI 逼出来的三个跨平台问题

本地 GCC 编译全绿，上 CI 才暴露：

**1. `cstdint` 缺失（12 个文件）**
`src/image.hpp` 用了 `std::vector<uint8_t>` 却没 `#include <cstdint>`。
GCC 通过其他头文件的间接包含放行了，mingw 直接报 `template argument 1 is invalid`。
**依赖间接包含迟早会在别的编译器上翻车**，已给全部 12 个文件显式补上。

**2. `struct tm` 未初始化**
`zip.cpp` 的 `dosTime()` / `dosDate()` 声明了 `struct tm tmBuf;` 却没初始化，
而 `localtime` 失败时不会写入 —— 直接读未初始化字段是 UB。改成 `struct tm tmBuf{}`。

**3. `std::cyl_neumann` 等标准特殊函数不存在（Android）**
`std::cyl_bessel_i/j/k`、`std::cyl_neumann` 是 C++17 的"数学特殊函数"，
**libstdc++ 有，libc++（Android NDK 默认）没有**，编译直接失败：

```
error: no member named 'cyl_bessel_i' in namespace 'std'
```

改为自持实现（`src/bessel.hpp`），顺带统一精度行为，并已与 SciPy 逐点核对。
过程中修掉两个自己写错的地方：

- **Y_0 的级数符号**：把 `(-1)^(k+1)` 写成 `(-1)^k`，x=0.5 时得 -0.5222，正确 -0.4445
- **Y_1 不能靠 Wronskian 反推**：`Y_1 = (J_1·Y_0 + 2/(πx))/J_0`，但 **J_0 有零点**
  （第一个在 x≈2.4048），在那附近除法会把结果放大到荒谬的值。改成直接用级数

另外 `M_PI` 在 MinGW 严格 ANSI 模式下不定义 —— 这个坑之前在别的文件里踩过一次，
`bessel.hpp` 里又踩了一次，已统一加兜底。

## 单元格样式与合并

`src/style.cpp`。支持字体（粗体/斜体/下划线/删除线/字号/颜色/字体名）、填充色、
边框（四边同一设置）、水平与垂直对齐、自动换行，以及合并单元格。

颜色写法灵活：`FF0000` / `#FF0000` / `F00`（三位简写）/ `FFFF0000`（ARGB，去掉 alpha）/
`red`（颜色名）都接受，统一归一成大写 `RRGGBB`。

### xf 必须由"格式码 + 样式"组合编号

**这是把样式接进 xlsx 时最容易写错的地方。** OOXML 的一个 `xf` 同时编码
`numFmtId + fontId + fillId + borderId + alignment`，所以索引必须由**组合**决定。
若让格式码和样式各自编号，一个格子既设格式又设样式时，其中一个会被静默覆盖。

现在 `StyleSet::xfIndexFor(code, style)` 按组合去重，相同视觉效果的格子共用同一个 xf
（50 个同样粗体的格子只产生 1 个字体条目，不是 50 个）。

**已通过 openpyxl 交叉验证**：合并区域 `A1:D1`、粗体、字号 14、红色字体、居中、
黄色填充、细边框、千分位格式、右对齐全部正确——尤其"格式码与样式并存且都生效"这条，
正是组合编号要解决的问题。

### 三个实现上踩过的坑

- **`fills` 的前两个被 OOXML 占死**（`0=none`、`1=gray125`），自定义填充从索引 2 起。
  从 1 起会导致背景色整体错位一格。
- **fonts / borders 必须先登记完再输出**。边写 `<fonts count="N">` 边登记的话，
  count 写的是登记前的数量，而 xf 引用的 fontId 会超出表长——文件照样能生成，但样式全丢。
- **空格式码不能去比对内建 ID**。`builtinNumFmt` 对未定义的 ID 也返回空串，
  拿 `""` 逐个比对会匹配上第一个返回空串的 ID（比如 23），
  于是 General 的格子被写成一个莫名其妙的 numFmtId。
- **读取端 `s` 属性不要 -1**。`s` 直接就是 `cellXfs` 下标，读取时把 cellXfs 逐个解析成
  数组，口径已一致；再减 1 会让所有格子的样式跑到前一个格子上。

### 四个容易埋雷的点

- **CJK 必须按 2 个显示列算宽**。一个"销售额"按 3 列裁切会吃掉后面一整列，整个网格错位。
- **退格必须按码点删**。按字节删会留下半个汉字，屏幕上变成乱码。
- **输入 `12abc` 不能静默变成 `12`**。必须用严格数值解析，不能用 `strtod` 的部分匹配。
- **修饰键藏在 CSI 序列的中间参数里**。只认最终字符的话 `Shift+↑` 和 `↑` 完全一样，选区没法用。

### 另两处设计取舍

- **撤销存单元格快照，不存整表快照**。大表上每次编辑复制整表不可接受，
  而一次改动通常只涉及很少的格子。公式写错时不进撤销栈。
- **表名以 Sheet 自身为准**。工作簿里另存了一份名字记录，若只改 Sheet 而不同步，
  就会出现界面显示新名、存盘写旧名——这个 bug 只在存盘后读回来才看得出来，
  所以 `make verify` 里加了多表中文表名的往返校验。

### 前置：装 mingw-w64

```bash
# Debian / Ubuntu
sudo apt install mingw-w64
# Fedora
sudo dnf install mingw64-gcc-c++ mingw64-zlib-static
# Arch
sudo pacman -S mingw-w64-gcc
# macOS
brew install mingw-w64
```

Windows 本机推荐 MSYS2：

```
pacman -S mingw-w64-x86_64-gcc mingw-w64-x86_64-zlib
```

然后把 `C:\msys64\mingw64\bin` 加进 PATH。

脚本会**优先找静态 zlib**：找到 `libz.a` 就静态链接，
这样目标机器上不用额外带 `zlib1.dll`。

### 跨平台支持做了什么

原来只有 POSIX 终端后端。`enterRaw()` 在没有 termios 的平台上直接返回
`false` —— 打出来的 EXE 只能渲染一帧就退出，**完全不能交互**，等于没用。
所以补了完整的 Windows 控制台后端：

| 能力 | POSIX | Windows |
|---|---|---|
| 原始模式 | `tcsetattr` | `SetConsoleMode`，关 `ECHO/LINE/PROCESSED_INPUT` |
| 中文 | 默认 UTF-8 | `SetConsoleCP/OutputCP(65001)`，**不做的话中文全是乱码** |
| 颜色 | ANSI SGR | 开 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`，否则 ANSI 被当字面文本 |
| 方向键 | `read` | 开 `ENABLE_VIRTUAL_TERMINAL_INPUT`，让键以 `ESC[A` 送来 |
| 读取 | `select` + `read` | `GetNumberOfConsoleInputEvents` + `ReadConsoleInput` |
| 窗口尺寸 | `ioctl TIOCGWINSZ` | `GetConsoleScreenBufferInfo` 的**窗口矩形** |

**关键设计**：开 `ENABLE_VIRTUAL_TERMINAL_INPUT` 后，方向键会以
`ESC [ A` 这种 ANSI 序列送来，于是现有的 `parseKeys` 可以原样复用 ——
不用再写一套扫描码映射表。这是省事且不易错的选型。

两个容易漏的点：

- **`leaveRaw()` 必须恢复控制台模式**，否则退出后用户的 shell 还是原始模式，
  看起来像"终端坏了"（不回显、换行失效）。
- **窗口尺寸用 `srWindow` 而不是缓冲区大小**，缓冲区可能比可见窗口高很多，
  用来算行会得到错误的高度。

### 交叉编译时踩到的两个坑

**一、`M_PI` 在 Windows 下不存在。**

`M_PI` 是 POSIX 扩展而非 C++ 标准，MinGW 在 `-std=c++17`（严格 ANSI）下
不定义它。涉及 `canvas.cpp` / `chartpdf.cpp` / `pdf.cpp` / `render.cpp`
四个文件，共 10 处。已在这四个文件里加 `#ifndef M_PI` 保护补齐，
Linux 侧不受影响（系统已有定义时不重复定义）。

**二、Debian 的 `mingw-w64` 不含 zlib 头文件。**

`mingw-w64` 只是元包。少了 `libz-mingw-w64-dev`，编译 `canvas.cpp` /
`zip.cpp` 时会报 `zlib.h: No such file or directory`。
`build_exe.sh` 现在会检测并在缺失时给出明确的安装提示。

### `localtime_s` 的签名陷阱

原代码在 `_WIN32` 下用 `localtime_s(&tmBuf, &t)`。这个函数的参数顺序
**在 MSVC 与 C11 标准里是相反的**，MinGW 在严格模式下还可能隐藏它 ——
交叉编译最容易在这里翻车。

改成 C89 的 `localtime` / `gmtime`：MSVC 和 MinGW 都有，没有签名歧义。

### 没有 mingw 也能查 Windows 分支

交叉编译环境常常没有 mingw，但 Windows 代码路径又最容易在"没人编译过"的
情况下烂掉。所以加了 `make wincheck`：用 `tools/winshim/` 下的最小
Windows API 头（只提供签名、不实现行为）做**语法检查**。

```bash
make wincheck
```

这个 shim 只验证类型与函数名正确，**不保证运行时行为** ——
真要确认能跑，还是得 `./build_exe.sh` 编出 EXE 在 Windows 上试。

## 功能与代码审计

一次完整审计。**不是靠读代码，而是写程序跑代码** —— 重点找
"声称实现了、实际不工作"的函数。

### 审计暴露的结构性问题

**176 个函数（36%）此前没有任何测试覆盖。** 冒烟测试只保证
"能调用、不崩溃"，而本次发现的 bug 全部**能通过冒烟测试**：
返回 0 不崩溃、返回错误值也不算未实现。只有比对数值才抓得到。

### 查出并已修复的问题

| 问题 | 现象 | 根因 |
|---|---|---|
| 重复实现 | `PERMUTATIONA` 恒 0；`F.DIST(...,FALSE)` 恒 0 | 同名函数在两个 .cpp 各注册一次 |
| 标准差用错 | `KURT({1,2,3,4,5})`=2.625（应 -1.2） | 用了总体标准差，Excel 用样本 |
| 反函数求解方向反了 | `CHIINV(0.5,5)`=100（应 4.35） | 对递减函数用了递增二分 |
| 左尾/右尾搞反 | `TINV(0.5,10)`=-0.6998（应为正） | 双尾反函数应取右尾 |
| 周数差一周 | `ISOWEEKNUM(2024-1-1)`=2（应 1） | 基准用 1 月 1 日而非 1 月 4 日 |
| 闰年多一天 | `YEARFRAC(2020→2021)`=1.00278（应 1） | 序列号被当成天数送进 `civilFromDays` |
| 付息期多算 | `COUPNUM(2024,2025,2)`=3（应 2） | 用平均月长再 `ceil` |
| 参数错位 | `BETADIST(0.5,1,1)`=`#VALUE!` | 旧式签名无 cumulative 参数 |
| 引用语义 | `ISREF(A1)` 恒 FALSE；`OFFSET` 全错 | 单格引用求完值就是标量，无从区分 |
| 格式化 | 进制转换多前导零；复数留 1e-16 噪声 | 默认补零；未清理浮点残余 |

### 两个跨函数的通用坑

**一、重复实现 —— 谁生效取决于未规定的初始化顺序。**

`registerFunction` 用的是覆盖语义，而 C++ 不保证跨编译单元的静态初始化顺序。
所以同名注册两次时，生效者是不确定的；更糟的是两份实现语义可能不同
（`F.DIST` 那两份，一份对一份错）。

现在 `registerFunction` 会登记重复项，测试断言必须为 0 条
（见 `duplicateRegistrations()`）。这条防线已经抓到过 11 起。

**二、引用语义必须在 AST 层特判。**

`ISREF(A1)` 和 `OFFSET(A1,1,0)` 需要知道"参数在语法上是不是引用"。
但单格引用求完值就是个标量，传到函数手里时已无从区分
"A1 里的 42"和"数字 42"。所以必须在求值前、拿着 AST 节点判断。

这与 `IF` 的惰性求值、惰性区域白名单用的是同一个位置和同样的理由。

### 第二轮：数组形状与空参数

针对第一轮后仍未覆盖的函数继续审计，又查出三类：

| 问题 | 现象 | 根因 |
|---|---|---|
| 转置方向反了 | `TOROW({1;2;3})` 返回 3 行 1 列 | 直接复用了生成"一列"的辅助函数 |
| 标量 `new_x's` 被忽略 | `TREND({2,4,6},{1,2,3},4)` 返回 `{2,4,6}` 而非 8 | 只认数组参数，标量整段跳过 |
| 空参数不可用 | `SORT(A1:A3,,-1)` 解析失败 | 解析器要求每个参数都是合法表达式 |

第三类影响面最大：`SORT(A,,-1)`、`VLOOKUP(x,A:B,2,)`、`OFFSET(A1,1,,3,2)`
这一批 Excel 常见写法此前**全部不可用**。现在加了 `NodeKind::Missing`
占位节点。

### 一个只有形状断言能抓到的 bug

`TOROW` 那一条：数值本身是对的（都是 1,2,3），只有连形状一起比
（`1x3` vs `3x1`）才暴露转置方向反了。所以审计里专门加了数组形状断言。

### 我自己的坐标错误

审计时**两次**把 `setValue(列, 行)` 写成 `(行, 列)`，于是得出
"DSUM 家族全错"的假结论。修正坐标后 10 个数据库函数全部正确。
这两个用例现在也把坐标语义钉住了，附了注释警告。

### 第三轮：针对"零覆盖"函数的专项审计

第二轮后仍有 **141 个函数（28%）在 tests/ 里一次都没被提及**。这一轮逐个
跑它们，找出三类真 bug：

| 问题 | 现象 | 根因 |
|---|---|---|
| 右尾反函数方向反了 | `F.INV.RT(0.05,5,5)`=0.198（应 5.05） | 多减了一次 `1-p`，求的是左尾分位数 |
| EXC 百分位少加 1 | `PERCENTRANK.EXC({1,2,3,4},1)`=0（应 0.2） | 分子是 `below` 而非 `below+1` |
| 复数格式不一致 | `IMTAN("0")` 输出 `0+0i`，其余是 `0` | 内联了一套自己的格式化，没复用 `cxStr` |

**F.INV.RT 那条最隐蔽**：0.198 和 5.05 恰好互为倒数（F 分布性质
`X~F(d1,d2) ⇒ 1/X~F(d2,d1)`），所以结果"看起来是个合理的 F 值"，
只有拿统计表标准值对照才暴露。现在用**标准值 + 往返自洽**双重钉死。

**PERCENTRANK.EXC 用关系断言抓到**：它与 `PERCENTILE.EXC` 必须互逆，
而 `PERCENTILE.EXC({1,2,3,4},0.2)=1` 却对应 `PERCENTRANK.EXC(...,1)=0`，
两个函数对不上，必然有一个错。这类"两个函数互为反函数"的关系，
是最省力的验证手段——不需要查表，只需要让它们自洽。

### 我又写错了几次期望

审计中我**四次**把期望写错、而引擎是对的：

- `DATEVALUE("2024-03-15")`：我算成 45367，实际 45366
- `EXP(1)`：我按截断值 `2.718281828` 比，实际输出完整精度
- `RANK.AVG`：我以为默认升序，Excel 默认**降序**
- `ACCRINTM(...,basis=1)`：我用 1461/365，Excel 用平均年长 **365.25**

另外 `TBILLEQ` 和 `RECEIVED` 返回负数，一度以为是崩溃级 bug，
查下来是我**传错了参数**——`TBILLEQ` 第三参是贴现率不是价格，
`RECEIVED` 第四参是贴现率不是面值。

### 五轮专项审计后的覆盖率：495 / 495 全部有断言

针对"零覆盖"函数连做五轮专项审计，未提及函数数：

```
141  →  71  →  46  →  24  →  0
```

**但这不等于"全部验证正确"。** 要区分两层：

- **语义正确性** —— 强断言（手算/查表/往返自洽）覆盖了大部分；

  例如 `ACCRINTM` 的 basis=1 年长口径、`BAHTTEXT` 的占位实现。

### 测试期望写错的三处

审计时也发现**我自己的测试期望写错了**（照着当时的实现写，而不是照着

`FORECAST.LINEAR` 与 `CRITBINOM` 则相反 —— 是我的期望记错了参数顺序，
实现是对的。

### 第四轮：付息期锚点 —— 三个函数互相自洽，但整体都错

`COUPDAYS` 原先**完全忽略结算日与到期日**，直接返回 `365/freq`：

```
COUPDAYS(2024-3-1, 2025-1-1, 2, 1) = 182.5      ← = 365/2
```

而同一付息期的另两个函数给出 `COUPDAYBS=60`、`COUPDAYSNC=122`，相加是 **182**；
`COUPNCD-COUPPCD` 也是 **182**。三条路径都对不上 182.5 —— 所以第一版修完
（改成按结算日所在年份取固定月份档，freq=2 → 1月/7月）后**三条路径完全一致了**，
却仍然是错的：

```
COUPDAYS(2023-5-15, 2030-11-15, 2, 1) = 181     ← 按 1/15~7/15 算
正确 = 184                                       ← 付息日应由到期日 11/15 往前递推
```

**根因**：Excel 的付息日序列由**到期日 + 频率**决定，向前逐周期递推，与结算日
所在年份无关。三个函数共用同一个错误锚点，所以互相"自洽"，只比对数值永远发现不了。

现在统一走 `couponPeriod()`，以到期日为锚点。已验证频率 1/2/4、闰年/平年、
结算日在上下半年、结算日恰在付息日、basis=0/1 全部自洽。

### 第五轮：DISC 完全忽略 basis

```
DISC(2024-1-1, 2024-7-1, 97, 100, 1) = 0.06        ← 0.03 × 360/180，按 30/360
正确                                  = 0.060330    ← 0.03 × 366/182，闰年实际天数
```

第 5 个参数 `basis` 被丢弃了。**判据不是查表，而是 `DISC` 与 `PRICEDISC` 必须互逆**：
把 `DISC` 的结果喂回 `PRICEDISC` 应还原成原价 97，而 0.06 还原出的是 97.0164。
同族的 `INTRATE`/`RECEIVED`/`YIELDDISC` 本来就用 `yearFrac`，是对的 —— 只有一个函数
漏了，才显得格外隐蔽。

### FREQUENCY 的方向

返回的是行向量 `1x3 {2,2,1}`，Excel 是**列向量**（竖向溢出）。数值全对，只有比对
形状才暴露。这类 bug 横向溢出时"看起来没问题"，是形状断言存在的理由。

### 一个反复踩了三次的坐标陷阱

`Sheet::setValue` 的签名是 `setValue(列, 行)`，与 `setFormula` 一致，**和直觉相反**。
我按 `(行, 列)` 写过三次，每次都得出"引擎算错了"的假结论 —— 数据其实被铺到了同一行
的不同列上。第三次已在用例里加了显式注释警告。

### 测试辅助自身的缺陷

`arr()` 断言里错误值被格式化成 `#E6`（枚举序号）而不是 `#N/A`。这是**测试代码**的问题
不是引擎的，但它会让所有含错误的数组断言都写不对期望。已改用 `errText()`。

## 压力测试与鲁棒性

功能测试喂正确输入、验证结果；这两组专门喂**错误输入**和**极端规模**，
只验证一件事：**能否安全失败，而不是崩溃**。

`make test` 会自动跑这两组。压力测试每项都带耗时阈值，超了就 FAIL：
不是断言精确值，而是对"慢到不可用"给出明确结论。

### 压力测试实测数据

```
写入 100,000 个单元格              35 ms
全量重算 1,000 条 SUM(100列)       44 ms
构建 + 递归求值 5,000 层依赖链      5 ms
解析 + 求值 10,000 项连加           6 ms
1,000 格环形循环引用检测            0.5 ms
保存 100,000 格 xlsx              450 ms
读回 100,000 格 xlsx              173 ms
50,000 点折线图渲染 PNG           236 ms
反复编辑 / 反复解析的内存增长        0 KB
```

### 压力测试揪出的六个崩溃

每一个都是实测崩溃，不是理论风险：

| 输入 | 后果 | 修法 |
|---|---|---|
| `=((((...1...))))` 5000 层 | 解析器递归爆栈，段错误 | 递归深度上限 4000 |
| `=1E400` | `std::stod` 抛 `out_of_range` 未捕获，terminate | 按 Excel 语义饱和：上溢→`#NUM!`，下溢→0 |
| `=A1:XFD1048576` | 展开 170 亿个元素，OOM 被杀 | 区域展开上限 1048576 个 |
| `%%$` | 词法器位置停滞，死循环产出空 token，OOM 被杀 | 强制 token 必须前进 + `run()` 兜底 |
| 变异过的 xlsx | XML 深层嵌套，`parseNode` 爆栈，段错误 | XML 嵌套上限 200 |
| 压缩包炸弹（204KB→600MB） | 解压无上限，内存吃满 | 单条目解压上限 256MB |

其中 `%%$` 和 XML 爆栈是**模糊测试**跑出来的 —— 手工测试想不出这两种输入。

### 两处性能修正

- **大图表渲染**：原先每个点都画标记 + 数值标签，5 万点要 11 秒。
  改成点少才标注（>500 点不画标记、>50 点不画标签）后降到 236ms，**快 47 倍**。
  这不是牺牲效果 —— 点多时标记和标签会糊成一团，本来就该只画趋势线。
- 同时修正了 SVG 输出的同类问题：5 万个 `<circle>` 会让文件涨到几十 MB。

## 已知边界（诚实标注）

### 函数覆盖的两个层次

声称"495 个函数"时，要区分两件事：

- **可调用性**（495/495）：`tests/test_smoke.cpp` 逐个调用全部函数，
  确认能被解析、求值不崩溃、不返回未实现类错误。**全部通过。**
- **语义正确性**（部分）：精确断言只覆盖了约六成函数。其余仅有冒烟保障，
  **没有验证过计算结果对不对**。

这个区分不是文字游戏。VDB 就藏在未覆盖的那一批里：它声明最少 4 参、
实现却访问第 5 个，只传 4 参时越界读直接段错误 —— 此前没有任何测试碰过它。
冒烟测试固化后，这类"函数表里有名字但实际不能用"的问题会被自动暴露。

- **PRICE / YIELD / COUP\***：覆盖常规年付/半年付/季付，未处理首个/末个奇数付息期
- **不防御"合法但巨大"的构造**：区域展开上限 1048576 个元素、
  单个 XML 部件解压上限 256MB。超出会明确报错，这是有意设定的边界而非缺陷
- **BAHTTEXT 是占位实现**：返回 `1.00 Baht` 这样的占位文本，**不是**泰文金额读法。
  真正的 BAHTTEXT 需要泰语数字规则（สิบ/ร้อย/พัน/หมื่น/แสน/ล้าน 进位，
  以及 เอ็ด/ยี่ 等特殊读法），这里不编造泰文
- **FORECAST.ETS.STAT 的 MASE（stat=4）返回 `#N/A`**：该统计量需要朴素季节性
  预测的残差序列，引擎未保存。宁可返回 #N/A 也不编造数值（曾一度返回硬编码 1.0，
  会让调用方误判模型可用）
- **整列引用的行数语义**：`ROWS(A:A)` 在 Excel 是 1048576，这里返回已用区域高度。
  对 SUM/COUNT/COUNTA/VLOOKUP 这类用法结果一致，完整支持需要引入"稀疏区域"值类型
- **数字格式未覆盖**：分数 `# ?/?`、泰文/印度等 locale 格式、`[DBNum]` 类东亚数字；
  颜色与 `*`/`_` 只解析不渲染（需要列宽，且不影响数值正确性）
- **共享公式 `t="shared"` 已支持偏移展开**：找不到主格时降级为已算出的值并告警，不静默丢格
- **OFFSET 的锚点反推**：依赖当前单元格上下文，跨表或多区域场景未充分验证
- **日期以序列号存取**：数字格式的日期还原交给上层，引擎不做隐式类型判断
- **点阵字体不含中文**：PNG 里的中文显示成占位方框，SVG / PDF 走系统 TTF 所以正常
- **样式只覆盖四边相同边框**；每边不同样式、渐变填充未实现
- **数据验证的 date / time 退化为序列号比较**：界面不解析日期输入，
  所以"日期必须在某区间"实际只能按数值区间用；下拉箭头在终端也无对应物
- **条件格式缺 dataBar / colorScale / iconSet / containsText**：前三者是图形化呈现，
  需要独立绘制通道；终端只有 8 色，RGB 按"亮度+主色分量"近似映射，不追求准确
- 未实现：宏（按调研结论，VBA 宿主对象模型无公开规范，不可行）
- **批注不生成 VML**：Excel 里看不到批注三角标记，需"显示批注"才看得到内容
